# File Structure

Read this before Phase 2 (partitioning) and Phase 4 (per-region pages).
It pins down the directory layout, the slug rules, the membership test,
and the cross-link conventions so the output is predictable across
exports.

## Directory layout

```
docs/                           ← target dir, default .claude/live-render-docs/
├── index.md                    ← always present; entry point
├── orphans.md                  ← omitted if zero orphans
├── <region-slug-1>.md          ← one per region
├── <region-slug-2>.md
└── ...
```

No subdirectories. No assets directory. No frontmatter. The output is
flat plain-markdown so it renders identically in GitHub, GitLab, a
phone's notes app, and a Slack preview.

## Slug rules

Region slugs come from `metadata.title`:

1. Lowercase
2. Strip diacritics (NFD then drop combining marks)
3. Replace non-`[a-z0-9]+` runs with `-`
4. Trim leading/trailing `-`
5. If the result is empty (titles like `"🔥🔥🔥"`), fall back to
   `region-<short-id>` where `<short-id>` is the first 6 chars of the
   region's entity id.

Two regions whose slugs collide should be suffixed with `-2`, `-3`, etc.
in document-order. Don't try to be clever about disambiguation; the
collision is unusual enough that a numeric suffix is fine.

```ts
function slugify(title: string, fallbackId: string): string {
  const base = title
    .normalize('NFD')
    .replace(/[̀-ͯ]/g, '')
    .toLowerCase()
    .replace(/[^a-z0-9]+/g, '-')
    .replace(/^-+|-+$/g, '')
  return base || `region-${fallbackId.slice(0, 6)}`
}
```

## Membership test

A node belongs to a region if the node's bounding-box centre is inside
the region's bounding box. Matches the live-render runtime's quadtree
hit-test, so the markdown grouping aligns with what the canvas shows.

```ts
function isInside(child: Entity, parent: Entity): boolean {
  const cx = child.spatial.x + child.spatial.width / 2
  const cy = child.spatial.y + child.spatial.height / 2
  return (
    cx >= parent.spatial.x &&
    cx <= parent.spatial.x + parent.spatial.width &&
    cy >= parent.spatial.y &&
    cy <= parent.spatial.y + parent.spatial.height
  )
}
```

Regions are assumed disjoint. If a node's centre falls in two regions
(overlapping regions — rare but possible), pick the smaller-area region
deterministically and log a warning to the user so they can clean up the
canvas.

## Edge assignment

Edges belong to *both* endpoint pages. This means a cross-region edge
appears in two Mermaid diagrams — once on each side. The foreign endpoint
is rendered as a node with a label like `[other-region/node-title]` and
the line becomes a `[[markdown link]]` in the surrounding prose. See
`mermaid-patterns.md` for the exact syntax.

If an edge points to an entity that no longer exists in `world.entities`,
drop the edge silently. (Edges should not exist in this state — but a
mid-flight world snapshot can show this.)

## Annotation assignment

For each annotation, count how many of `enclosedEntityIds` are in each
region. Assign the annotation to the winning region. Ties go to the
region whose centre is closest to the annotation's centre.

If `enclosedEntityIds` is empty (annotation in dead space), put it on
`orphans.md` rather than guessing.

## Cross-link conventions

Use relative paths with the `.md` extension. GitHub, GitLab, and most
markdown viewers handle these correctly:

```markdown
See [Platform region](./platform.md) for the auth service.
```

Inside Mermaid diagrams, use the `click` directive to make foreign nodes
clickable. See `mermaid-patterns.md`.

For *node-level* cross-links from prose, use the entity id as the anchor
on the entity table row:

```markdown
The [billing service](./platform.md#svc_billing) emits …
```

Generate table rows with explicit anchors so this works:

```markdown
| ID | Title | Kind |
| --- | --- | --- |
| <a id="svc_billing"></a>`svc_billing` | Billing | Component |
```

## Footer convention

Every page (including `index.md`) ends with a generation footer:

```markdown
---

_Generated by `live-render-to-markdown` from `<workspace_path>` at
`<ISO 8601 timestamp>`. To regenerate, re-run the skill against the
live-render workspace._
```

This is the only metadata in the doc — no frontmatter, no hidden
machine-readable blob. The skill is meant to be re-runnable; readers
shouldn't need to track which version of the canvas they're looking at.
